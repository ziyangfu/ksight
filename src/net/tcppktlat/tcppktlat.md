# tcppktlat 诊断指南

## 概述

`tcppktlat` 测量 TCP 连接中数据包从到达网络协议栈TCP层到被用户态进程读取（PICKUP）之间的时间差。它能精确揭示“协议栈到应用层”之间的内部处理延迟。

**核心场景**：

1. **应用处理瓶颈**：服务器接收到包后，过了很久才尝试读取（如线程池过载、忙于 CPU 密集型操作）。
2. **数据处理路径故障**：识别报文在内核队列中排队时间过长的情况。
3. **延迟抖动识别**：测量由于延迟确认（Delayed ACK）或 Nagle 算法造成的微小停滞。

## 命令行参数

| 参数 | 缩写 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `--pid`       | `-p` | uint32 | 0 | 仅追踪指定 PID |
| `--tid`       | `-t` | uint32 | 0 | 仅追踪指定 TID |
| `--timestamp` | `-T` | bool | false | 在输出中包含时间戳 |
| `--lport`     | `-l` | uint16 | 0 | 过滤特定的本地端口 |
| `--rport`     | `-r` | uint16 | 0 | 过滤特定的远程端口 |
| `--wide`      | `-w` | bool | false | 宽列输出（适配 IPv6 地址展示） |
| `--verbose`   | -    | bool | false | 打印调试详细信息 |
| `delay`       | -    | uint64 | 0 | 仅追踪超过此延迟（微秒 us）的记录 |

## AI 逻辑与调用指引

### 何时调用

AI Agent 在观测到以下异常时，应考虑调用此工具：

- **P99 响应延迟激增**: 但网络层 RTT（`tcpconnlat`）保持正常。
- **CPU 负载或调度异常**: 怀疑进程调度延迟导致了报文读取缓慢。
- **延迟特征识别**: 协助确定是否触发了延迟确认机制（通常伴随 40ms/200ms 的延迟倍数）。

### 输出解读 (AI 视角)

- **Latency (us)**: 输出以微秒为单位。AI 应重点分析高分位数（P95, P99）的延迟值。
- **PID/TID**: 指明是哪个应用线程存在读取阻塞。

## 与相关工具的关系

- **与 tcptop 的联动**: 当 `tcptop` 显示某个流吞吐量大但 `tcppktlat` 显示延迟极高时，说明应用层已经跟不上内核的报文接收速度。
- **与 tcpretrans 的联动**: 如果因为处理太慢导致接收窗口填满，可能会诱发重传。

垂向全链路跟踪功能开发

该功能将使 ksight 从一个“零散的内核观测工具集”进化为“具备业务感知能力的车载协同诊断平台

开发原因：开发垂向全链路跟踪功能，可以实现，从应用到中间件，到内核，再到物理层的，垂向全链路跟踪
说明白，一个数据包，它是哪个应用发出的，发给谁的，中间经过了哪些重点函数，或者哪些层，各自都耗时多少。这样可以方便开发人员定位问题。
理想情况下，它应该是可以包括：
从应用SOA服务，到中间件，再到内核，内核还包括了多层，例如传输层、网络层、数据链路层等。

传统的跟踪方案，主要是日志追踪，也就是需要开发者在编写代码时尽可能全地打印日志，再通过关键字段从日志中搜集筛选出与业务逻辑相关的日志数据，进而拼凑出业务执行的现场信息。
这个方案存在日志筛选困难、日志分析耗时、其次如果大量打印，可能会影响性能
现在我们的方案

现在我们的方案，是希望结合eBPF技术在内核的无侵入式观测、uprobe或者其他的用户态程序插桩技术（退一万步说，退化到日志跟踪），以及车载应用开发依赖的整车以太网通信配置及SOA通信汇总表（车内是个静态网络，IP地址、SOA的服务ID等，都是由网络工程师静态配置的，我们可以读取绑定）

因此，从实现上，我们可以做到如下的几个事情：
1. 用户态程序读取SOA配置汇总表，建立IP地址与SOA服务ID的映射关系（当前控制器、对方的控制器名，我的和对方的IP地址，服务ID，这个SOA服务的描述，VLAN ID是多少等）
2. 然后就是中间件，这部分是比较麻烦的，插桩技术需要中间件本身的支持，主要是获取这个数据，流经中间件的重点函数都是哪些。这一个部分暂时是和薄弱点，后续可以考虑自己开发中间件，并插桩。把App到中间件的那个节点，能获取一个时间戳吗，那么就可以记录数据进入到系统调用的时间点，然后计算出中间件部分，总共耗时多少。
3. 进入内核端的数据跟踪与耗时统计，这个部分可以让现有的nettrace 跟踪网络数据包。它可以打印如数据包在内核中的重点函数的链路。如果这个数据包是进程间通信的，例如UDS与共享内存，也可以考虑用eBPF的特定工具去跟踪。这是链路跟踪部分，还可以通过netwatcher来实现，这个数据包在传输层、网络层以及数据链路层的耗时统计。对外的数据包，可以获得tcp的往返时间，例如通过tcprtt等类似的这种工具。
4. 还可以考虑动态检测，例如SOME/IP SD 的报文，如Find Service或者Offer Service，来动态的发现网络中的服务，并建立映射关系。

从汇总表能获得的信息：
1. 静态网络信息：IP地址、端口、VLAN ID、MAC地址，TCP/UDP协议等。
2. SOA服务信息：服务ID、方法ID、服务名称、实例ID、周期等。
3. 拓扑信息：哪些IP地址属于同一台物理设备（通过IP段或MAC地址推断）。
4. 业务关联：哪些IP地址和端口对应哪个SOA服务和方法。


串联的唯一key：
源IP + 源端口 + 目的IP + 目的端口 + 协议 + 报文特征（service ID + instance ID） + tid



目前能做到的事情：
1. 根据源IP + 源端口 +目标IP + 目标端口 实现网络数据包在内核中的链路跟踪，可以进行过滤输出，这部分通过nettrace实现。
2. 根据源IP + 源端口 + 目标IP + 目标端口，来定位这个数据包在内核每一层的分层耗时，这部分是用过netwatcher实现的。
3. RTT的获取，这部分可以通过netwatcher或者tcprtt实现。



为什么不在内核中抓取TCP的 payload，然后解析出应用层的header？
1. TCP是流式协议，数据在内核中是分片传输的，对于完整的报文，它可能涉及分片重组、还有可能重传。
对于一个sk_buff来说，它可能只包含一个完整的应用层报文，也可能包含多个应用层报文，还可能包含不完整的应用层报文。
2. 在内核的socket层，即数据包即将出内核，应用层应用会从socket缓冲区把数据读取走，在这部分，对于TCP来说，这个地方抓取的包，是完整的数据。同样因为是TCP是流式数据，会有粘包的情况，会把多个应用层的报文粘在一起，因此正常来说，需要类似固定字长拆包这种拆包方案，最终拆出完整的应用层报文，然后解析出应用层的header。

wireshark在数据链路层抓包，最终它有一个TCP报文重组的功能，会把TCP报文重组好，然后拆包显示。

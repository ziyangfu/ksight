# 复盘记录：TCP 字节流切割应对方案与“线程上下文染色”重构

## 1. 做的事情 (What was done)

针对 `e2etracer` 在处理复杂 TCP 流量（可能发生分段、粘包）时由于底层剥离无法准确提取应用层 16 字节 Payload 头的问题，彻底调整了架构思路。
我们弃用了“在内核全盘截取并强行尝试切片”的错误设想，转而落地了更加轻量、精准的**“Uprobe 注入 + 线程 TID 染色”**方案。同时，以此为契机清理了 BPF 的类型空间冲突，整合了 JSON 配置文件的加载检索，补充了底层的 BPF 解析指令。

## 2. 为什么这么做 (Why it was done)

* **客观事实限制**：TCP 作为字节流，与 UDP 面向报文的特性完全不同。应用层的 SOA 大包会在进入网卡前被拆分成多个 MTU 大小的串行 `sk_buff`；如果是高并发多个小的数据请求则会被 Nagle 算法粘包。强行要求底层按偏移剥离包头，其成功率极低，且毫无诊断价值。
* **避免过度工程化**：遵循 KISS 原则，如果需要在内核态用 BPF 去记录和重组 TCP 这条河中复杂的水流（追踪序列号和 Ack），逻辑将极度膨胀且消耗大量资源，违背诊断工具“低开销低侵入”的初衷。
* **正本清源**：问题的源头在于业务层知道数据是什么，因此将观测点适当上移（Uprobe 观测发送库函数），用线程身份关联上下文，这是最为可靠的高性能设计思路。

## 3. 怎么做的 (How it was done)

1. **BPF 上下文管理 (Map 设计)**：
   在 `e2etracer.bpf.c` 中新建了 `map_thread_context`。在应用中间件（如 vsomeip/DDS）发起发送请求时触发，立即以系统 `TID` 为核心标识录入 `ServiceID`。
2. **底层拦截与染色覆盖**：
   在 `fentry/ip_output` 中，BPF 获取发出此时系统调用的 `TID`，反查哈希表。成功查找到业务后裔便当场给 `sk_buff` 贴上 SOA 身份标签。（完成“染色”）
3. **针对性性能过滤优化**：
   不再无差别上传。将用户感兴趣的 `target_service_id` 直接传给内核态的 `rodata` 只读变量，内核态自行决定是否丢弃该上报，防止大量的无关 SOA 数据拖垮用户区性能。 
4. **命名空间与兼容性隔离**：
   系统性更名了 `trace_event` 等极易与内核 `<vmlinux.h>` 重复引用的原生结构符，防止系统头文件包含导致的宏碰撞问题。
5. **JSON 配置逻辑闭环**：
   实现完了 `SoaManager` 获取端点数据的检索匹配。如果数据包因某种原因（如 UDP 等未装载 Uprobe 但能看到 Payload 的）缺少标记，它可以通过 `ip:port` 或解析的 16bytes Header 双向回溯到用户可视的服务名称。

## 4. 结果是什么 (What is the result)

* **逻辑架构跑通**：现在 `e2etracer` 支持一条由 `[Uprobe 拿到应用信息] -> [传至 TID Map] -> [fentry 层取出染色] -> [Perf 传回结果]` 的完备底层闭环控制链。
* **代码稳定化**：消除了绝大部分由于未正确载入 `E2ETracer.skel` 前造成的类型冲突和编译隐患。
* **后续接入能力就绪**：预留了手动开关和配置模板（`soa_config.json`），用户可以用极少代价完成环境挂接。

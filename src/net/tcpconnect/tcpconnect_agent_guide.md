# tcpconnect 诊断与治理指南

## 概述

`tcpconnect` 是一个用于实时观测全系统 TCP 主动连接行为的工具。相比于 `netstat` 或 `ss` 这种快照类工具，`tcpconnect` 能够捕获到由于生存周期极短而难以被快照捕捉的连接动作，并能精准关联到发起连接的进程（PID/Comm）。

**核心功能**：
1. **连接追踪**：记录每一个成功的 TCP 出站连接。
2. **进程关联**：通过 eBPF 获取发起连接的进程 PID、命令名称及用户信息（UID）。
3. **多维过滤**：支持指定端口、PID、UID 的精细化监控。
4. **统计模式**：支持按流（五元组）统计连接发起频率。

## 核心原理

`tcpconnect` 通过在内核 TCP 连接发起路径上进行双向追踪实现：
1. **Entry 阶段**：挂载于 `tcp_v4_connect` / `tcp_v6_connect` 入口。此时连接尚未真正开始，eBPF 利用线程 ID (TID) 作为键，将 `struct sock *` 地址临时暂存在 Hash Map 中。
2. **Exit 阶段**：挂载于上述函数的返回处 (kretprobe)。当函数返回时，eBPF 从 Map 中根据 TID 取出对应的 `sock` 指针，此时可以安全地从该结构体中提取出源 IP、目的 IP、目的端口等关键信息。
3. **输出**：采集到的数据通过 Perf Event 缓冲区异步推送到用户态，避免阻塞内核网络路径。

## 命令行参数 (CLI Arguments)

| 参数 | 缩写 | 类型 | 说明 |
| --- | --- | --- | --- |
| `--pid` | `-p` | int | 仅监控指定进程发起的连接 |
| `--uid` | `-u` | int | 仅监控指定用户发起的连接 |
| `--port` | `-P` | list | 仅监控指定目的端口的连接（支持多个） |
| `--count` | `-c` | bool | 统计模式：不输出明细，仅在退出时打印各流的连接总数 |
| `--source-port`| `-s` | bool | 在输出中显示本地源端口 |

## AI 逻辑与调用指引

### 何时调用（场景决策）
AI Agent 在面临以下信号时应启动 `tcpconnect`：

1. **外部依赖排查**：业务报错“连接超时”或“服务不可用”，AI 需确认本地进程是否真的发起了向目标服务的请求。
2. **异常外联检测**：系统出现异常高负载或流量异常，AI 用于审计是否有不明进程在尝试连接外部服务器，或是否存在数据外泄风险。
3. **短连接风暴**：QPS 异常但当前连接数不高，调用 `tcpconnect -c` 确认是否存在大量频繁销毁的短连接，这通常是由于未启用长连接池导致的。

### 输出解读 (AI 视角)
- **发现目标 IP = 127.0.0.1**：进程可能在进行大量的本地 Loopback 通信，需检查本地服务发现或代理组件是否异常。
- **发现大量不同目的端口**：如果目标是单一 IP，可能存在扫描行为或配置错误的负载均衡器。
- **COMM 字段异常**：如果发起连接的进程名不符合业务预期（如 `/tmp` 下的执行文件），需触发安全报警。

## 相关工具联动

- **与 tcpaccept 联动**：`tcpconnect` 关注“谁连出去”，`tcpaccept` 关注“谁连进来”。两者合并分析可勾勒出完整的服务拓扑关系。
- **与 tcpconnlat 联动**：如果 `tcpconnect` 确认有连接发起，但业务反馈延迟高，应调用 `tcpconnlat` 测量握手具体消耗。
- **与 tcpretrans 联动**：如果在 `tcpconnect` 记录中发现目的 IP 正确但业务报错，需通过 `tcpretrans` 确认是否在握手阶段发生了 SYN 分片丢失导致的重传。

## 性能影响与局限性
- **性能影响**：在普通千兆网络环境下开销几乎不可察觉。在极高频（>10k/s）建连场景下会产生一定 CPU 波动。
- **局限性**：由于挂载在连接发起层，它无法探测到被内核底层协议栈直接拒绝的连接（如路由不可达），也无法探测由于防火墙（IPTables/NFTables）在 Drop 链丢弃的情况。
